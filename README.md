# AEGIS

**A**cademic **E**ditorial & **G**raduate **I**ntegration **S**ystem — from master's thesis to
scientific breakthrough. All in one place.

A .NET + Next.js monorepo. [.NET Aspire](https://aka.ms/aspire) orchestrates local
development; Docker Compose runs the stack everywhere else.

**Why the split.** `apps/` holds things that ship, `libs/` holds code shared between them,
`aspire/` holds development-only orchestration, and `infra/` holds environment assets that
are not application code. The AppHost lives outside `apps/` on purpose: it is never
deployed.

**A note on `apps/web/AGENTS.md` and `CLAUDE.md`.** Next.js writes these itself on every
`next dev`, to tell AI coding assistants that this major version has breaking changes.
Deleting them only recreates the diff on the next run, so keep them committed.

## 3. Local development

In development the services run as **host processes**, not containers: fast restarts, hot
reload, and a debugger you can attach. Only PostgreSQL runs in a container.

### 3.1 Prerequisites

| Requirement | Why |
|---|---|
| .NET SDK 10 | Builds and runs the API and the AppHost |
| Node.js 22+ | Runs the Next.js dev server |
| A container runtime | PostgreSQL (and pgAdmin, if enabled) |

Docker **buildx** and **Compose v2** are only needed for the container paths — the default
`dotnet aspire run` uses neither. They ship with Docker Desktop and OrbStack; on Linux they
are separate packages.

### 3.2 Installing the prerequisites

#### Windows

```powershell
winget install Microsoft.DotNet.SDK.10
winget install OpenJS.NodeJS.LTS
winget install Docker.DockerDesktop
```

Restart the terminal, then confirm:

```powershell
dotnet --version   # 10.x
node --version     # v22.x
docker info
```

Docker Desktop must be running before `aspire run` — the PostgreSQL container needs it.
WSL 2 is the recommended backend.

#### macOS

```bash
brew install --cask dotnet-sdk
brew install node
brew install --cask docker        # or: brew install --cask orbstack
```

Confirm:

```bash
dotnet --version   # 10.x
node --version     # v22.x
docker info
```

On Apple Silicon everything used here has native arm64 images, including
`postgres:18-alpine`.

#### Linux (Ubuntu / Debian)

```bash
# .NET SDK 10 — see https://learn.microsoft.com/dotnet/core/install/linux for other distros
sudo apt update
sudo apt install -y dotnet-sdk-10.0

# Node.js 22 (NodeSource)
curl -fsSL https://deb.nodesource.com/setup_22.x | sudo -E bash -
sudo apt install -y nodejs

# Container runtime
sudo apt install -y docker.io
sudo usermod -aG docker "$USER"   # log out and back in for this to take effect

# Only needed for the container paths (Web:Mode=container, docker compose)
sudo apt install -y docker-buildx docker-compose-v2
```

Confirm:

```bash
dotnet --version   # 10.x
node --version     # v22.x
docker info
```

> `docker-buildx` and `docker-compose-v2` are genuinely required on Linux. Docker's legacy
> builder cannot run Aspire's image builds, and Compose v1 (`docker-compose`) is
> end-of-life and cannot read this repository's `docker-compose.yml`.

### 3.3 First run

```bash
git clone <repository-url>
cd AEGIS

# Restores the pinned Aspire CLI and dotnet-ef from .config/dotnet-tools.json
dotnet tool restore

dotnet aspire run
```

That is the whole setup. The AppHost creates the database container, waits for it, starts
the API — which applies its EF Core migrations on startup — installs the frontend's npm
packages, and then starts the Next.js dev server.

The CLI prints the dashboard URL. Five resources start:

| Resource | Kind | Address |
|---|---|---|
| `postgres` | Container | Random host port (internal use) |
| `aegisdb` | Database | — |
| `web-installer` | Process | Runs `npm install`, then exits |
| `api` | Process | http://localhost:5180 — the dashboard also links its `/scalar` reference |
| `web` | Process | http://localhost:3000 |

**Timings.** The first run is slow — it pulls `postgres:18-alpine`, downloads NuGet
packages and installs npm dependencies. After that a warm start takes **about 15 seconds**
end to end, of which the npm check is ~0.3s and the Next.js dev server is ready in ~0.4s.

> The Aspire CLI is pinned as a local tool, which is why the command is `dotnet aspire run`.
> If you also have the CLI installed globally, plain `aspire run` works.

### 3.4 Day-to-day commands

```bash
dotnet aspire run                 # Start everything, attached to the terminal
dotnet aspire start               # Start in the background
dotnet aspire describe            # List resources with state, health and URLs
dotnet aspire logs <resource>     # Tail one resource's logs
dotnet aspire stop                # Stop the background AppHost

dotnet build AEGIS.slnx           # Build all .NET projects
cd apps/web && npm run typecheck  # Type-check the frontend
```

Frontend edits hot-reload. Backend edits need a restart of the `api` resource — either from
the dashboard or by restarting the AppHost.

### 3.5 Database migrations

Migrations live in `apps/api/Migrations/` and are applied **automatically every time the API
starts**. You only run the CLI to create one:

```bash
dotnet ef migrations add <Name> --project apps/api
```

`apps/api/Data/AegisDbContextFactory.cs` provides a design-time connection string, so this
works without Aspire running and without a live database.

To apply migrations manually against a specific database:

```bash
ConnectionStrings__aegisdb="Host=localhost;Port=5432;Database=aegisdb;Username=aegis;Password=..." \
  dotnet ef database update --project apps/api
```

## 4. Self-hosting with Docker Compose

Compose is the deployment path. Aspire is not involved: every service runs as a container
built from the same Dockerfiles the AppHost can build.

### 4.1 Steps

```bash
cp .env.example .env
```

Edit `.env` — at minimum set `POSTGRES_PASSWORD`, and set the public URLs to the hostnames
the browser will actually use:

```bash
POSTGRES_USER=aegis
POSTGRES_PASSWORD=<a real secret>
POSTGRES_DB=aegisdb
POSTGRES_PORT=5432

ASPNETCORE_ENVIRONMENT=Production
API_PORT=8080
WEB_PORT=3000

API_PUBLIC_URL=https://api.aegis.example.com
WEB_PUBLIC_URL=https://aegis.example.com
```

Then build and start:

```bash
docker compose up -d --build
```

| Service | Default URL | Image |
|---|---|---|
| `web` | http://localhost:3000 | Built from `apps/web/Dockerfile` |
| `api` | http://localhost:8080 | Built from `apps/api/Dockerfile` |
| `postgres` | `localhost:5432` | `postgres:18-alpine` |

### 4.2 Operating it

```bash
docker compose ps                 # Status and health
docker compose logs -f api        # Follow one service
docker compose up -d --build api  # Rebuild and replace a single service
docker compose down               # Stop, keep the data volume
docker compose down -v            # Stop and DELETE the database volume
```

### 4.3 What the stack does

- `postgres` has a health check; `api` waits for `service_healthy` before starting.
- `api` has a health check on `/alive`; `web` waits for it.
- The API applies migrations on startup, so a fresh volume becomes a working schema without
  a manual step.
- `infra/postgres/init/*.sql` runs **once**, only when the data volume is first created.
  Use it for database-level setup; EF Core owns the schema.
- Data lives in the named volume `postgres-data` and survives `docker compose down`.

### 4.4 Before exposing it publicly

- `POSTGRES_PORT` is published for debugging. Remove that port mapping when the database
  should stay on the internal network.
- Put a reverse proxy with TLS in front of `web` and `api`, and set `API_PUBLIC_URL` /
  `WEB_PUBLIC_URL` to the public hostnames.
- `NEXT_PUBLIC_API_URL` is baked into the client bundle at **build** time, so changing it
  requires `docker compose up -d --build web`, not just a restart.
- `/health` and `/alive` are unauthenticated. Keep them off the public ingress or put auth
  in front of them.
- The Scalar reference is off in Production. If you enable it with `Scalar__Enabled=true`,
  remember it publishes every route the API exposes.

## 5. Configuration

### 5.1 AppHost settings (development)

Everything Aspire starts is driven by the `AppHost` section of
`aspire/Aegis.AppHost/appsettings.json`:

```jsonc
{
  "AppHost": {
    "Services": {
      // PostgreSQL is always started; the API cannot run without it.
      "Api": true,
      "Web": true,
      "PgAdmin": false      // Opt-in database browser: admin@admin.com / admin
    },
    "Ports": {
      "Api": 5180,
      "Web": 3000
    },
    "Web": {
      // "dev" = Next.js dev server with hot reload. "container" = build apps/web/Dockerfile.
      "Mode": "dev",
      // Set to false to skip `npm install` when dependencies are known to be current.
      "InstallPackages": true
    }
  }
}
```

Override any value per machine without editing the file. Environment variables use the
double-underscore form, and `dotnet user-secrets` works too:

```bash
AppHost__Ports__Web=3010 AppHost__Services__PgAdmin=true dotnet aspire run
```

| Key | Default | Effect |
|---|---|---|
| `AppHost:Services:Api` | `true` | Start the backend |
| `AppHost:Services:Web` | `true` | Start the frontend |
| `AppHost:Services:PgAdmin` | `false` | Start pgAdmin, pre-connected to `postgres` |
| `AppHost:Ports:Api` | `5180` | Host port for the API |
| `AppHost:Ports:Web` | `3000` | Host port for the frontend |
| `AppHost:Web:Mode` | `dev` | `dev` or `container` |
| `AppHost:Web:InstallPackages` | `true` | Run `npm install` before starting the frontend |

### 5.2 Ports — where they live

| Environment | Where to change |
|---|---|
| Aspire (dev) | `AppHost:Ports:*` in `aspire/Aegis.AppHost/appsettings.json` |
| Docker Compose | `API_PORT` / `WEB_PORT` / `POSTGRES_PORT` in `.env` |
| Aspire dashboard | `applicationUrl` in `aspire/Aegis.AppHost/Properties/launchSettings.json` |

Ports are **pinned**, not assigned at random. Aspire's default is a random host port per
resource, which moves every URL on each restart, breaks open browser tabs and changes the
CORS origin the API is told about. The endpoints are declared with `IsProxied = false`, so
each process binds its port directly with no proxy hop.

The trade-off: if a port is already taken, startup fails loudly instead of quietly moving
somewhere else. That is the intended behaviour — a fixed port you can rely on is worth more
than a start that always succeeds at an unpredictable address.

Ports flow through to everything downstream. `API_URL`, `NEXT_PUBLIC_API_URL` and the CORS
origin the API receives are all derived from `AppHost:Ports`, so changing a port needs no
other edit anywhere.

### 5.3 API documentation (Scalar)

The OpenAPI document and the [Scalar](https://scalar.com/) reference UI are configured in
`apps/api/Configuration/ScalarConfiguration.cs` and driven by the `Scalar` section of the
API's appsettings:

```jsonc
{
  "Scalar": {
    "Enabled": false,               // appsettings.Development.json overrides this to true
    "RoutePrefix": "/scalar",
    "Title": "AEGIS API",
    "Theme": "Purple",              // any name from Scalar's ScalarTheme enum
    "DefaultClientTarget": "CSharp",
    "DefaultClient": "HttpClient",
    "PersistAuthentication": true
  }
}
```

| Endpoint | Serves |
|---|---|
| `/openapi/v1.json` | The generated OpenAPI document |
| `/scalar` | The interactive reference UI |

In development the Aspire dashboard shows a **Scalar** link on the `api` resource, next to
its endpoint URL, so it is one click away.

**`Enabled` is `false` in `appsettings.json` and `true` in `appsettings.Development.json`.**
A production deployment therefore has to opt in before publishing its API surface. Turn it
on for a Compose deployment with `Scalar__Enabled=true`, and consider putting it behind
authentication first — the document lists every route the API exposes.

Everything else is a plain configuration value, so the theme or the route can be changed per
environment without touching code:

```bash
Scalar__Theme=Moon Scalar__RoutePrefix=/docs dotnet aspire run
```

### 5.4 How the services find each other

The API reads a single connection string named **`aegisdb`**. Aspire injects it in
development; Compose passes it as `ConnectionStrings__aegisdb`. The application code is
identical in both.

The frontend reads two variables:

| Variable | Used by | Notes |
|---|---|---|
| `API_URL` | Server Components | Resolved at run time. In Compose it is `http://api:8080`, on the container network |
| `NEXT_PUBLIC_API_URL` | Browser | **Inlined at build time** by Next.js, so Compose also passes it as a Docker build argument |

CORS is configured from `Cors:AllowedOrigins`, which the AppHost and Compose both set to the
frontend origin.

### 5.5 Performance choices

| Choice | Why |
|---|---|
| `npm install --prefer-offline --no-audit --no-fund` | The installer runs on every start. These flags skip the registry when the cache already has the packages and drop the audit and funding reports. Measured on a warm tree: **1.43s → 0.29s** |
| No `--turbopack` flag | Turbopack is already the default bundler in Next.js 16; the flag only forces what is already on. `--webpack` is the opt-out. Verified: `▲ Next.js 16.3.3 (Turbopack)` |
| Services as host processes in dev | No image build per run. A warm start is ~15s; building images would add minutes |
| `IsProxied = false` | Removes Aspire's proxy hop between the browser and each service |
| Dockerfiles copy manifests before sources | Dependency restore stays cached until dependencies actually change |
| `output: "standalone"` | The production image carries only `.next/standalone`, `.next/static` and `public/` |

Turbo and pnpm workspaces are deliberately absent: they pay off in JavaScript monorepos with
shared internal packages, and `apps/web` is currently a single package with no internal
dependencies. They are worth revisiting when a second JavaScript package appears.

### 5.6 Design decisions

**PostgreSQL cannot be switched off.** There is no `Services:Postgres` flag. The API applies
its migrations on startup and cannot run without a database, so the toggle would only
produce a confusing failed start. This is noted in a comment in the JSON.

**Switching a service off removes it from the graph — it does not leave it stopped.** With
`Services:Api` set to `false`, the frontend still starts and still points at the configured
API port. That is exactly what you want when the backend is running from your IDE under a
debugger, or lives on another machine.

**Development runs processes, production runs containers.** The Dockerfiles are real and
used by Compose, but running them in development would cost an image rebuild per change and
give up hot reload and debugging. `Web:Mode=container` exists for when you specifically want
to verify the production image locally.

**Migrations run at startup.** Convenient for a single API instance and for a fresh Compose
volume. Move this to a dedicated migration job before running more than one replica — two
instances migrating concurrently is a race.

**`Note` is a placeholder.** The entity, its endpoints and the page that lists them exist to
prove the Web → API → PostgreSQL path end to end. Replace them with the real AEGIS domain.

## 6. Troubleshooting

**`unknown flag: --progress` when a service image builds**
Docker's legacy builder is being used. Aspire builds with BuildKit.
Fix: `sudo apt install docker-buildx` (Linux). Docker Desktop and OrbStack already include it.

**`docker compose` is not a command, or Compose rejects `docker-compose.yml`**
You have Compose v1, which is end-of-life and cannot read the Compose Specification.
Fix: `sudo apt install docker-compose-v2`.

**`The 'applicationUrl' setting must be an https address...`**
The AppHost's `http` launch profile needs `ASPIRE_ALLOW_UNSECURED_TRANSPORT=true`, which is
already set in `launchSettings.json`. If you added a profile, set it there too.

**`Developer certificates may not be fully trusted` on Linux**
Expected — the default `http` profile avoids it entirely. For HTTPS:

```bash
sudo apt install libnss3-tools
dotnet dev-certs https --trust
dotnet aspire run --launch-profile https
```

**"No response from http://localhost:5180"** on the frontend page
The frontend logs the real cause. Check the `web` resource logs in the dashboard, or
`dotnet aspire logs web` — the message includes the URL and the HTTP status or socket error.

**Address already in use on startup**
Ports are pinned deliberately. Either free the port, or change `AppHost:Ports:*` — see
[5.2](#52-ports--where-they-live).

**NuGet or npm downloads fail with `SSL connection could not be established` or `ETIMEDOUT`**
Transient network failures on large packages. Re-run the command; both restore incrementally
and keep what already downloaded.
